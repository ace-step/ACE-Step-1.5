1. Overview & Architecture

ACE-Step DJ is a single-file HTML/CSS/JS application (ui/dj.html, ~2300 lines) that provides continuous, infinite music generation using the ACE-Step V1.5 API. It acts as a "DJ" that continuously generates new segments of music, seamlessly stitching them together in real time using the Web Audio API.

Design Philosophy

  • Zero-dependency — no build tools, frameworks, or external JS libraries. Pure vanilla HTML/CSS/JS.
  • Single-file — everything in one HTML file for easy deployment (just serve it from any HTTP server).
  • Model-level continuity — uses ACE-Step's repaint task type for seamless audio continuation at the diffusion model level, not crossfade hacks.
  • Infinite playback — segments are generated in a pipeline, one ahead of playback, with automatic buffer underrun recovery.

2. Generation Pipeline

The engine maintains a simple pipeline with one segment always being generated ahead of playback:

Time ──────────────────────────────────────────────▶ Seg 0: [█████████████████████] playing Seg 1: [░░░░░░░░░░] generating... ↑ lookahead scheduler checks every 200ms

Pipeline Stages

StageBadge ColorDescription
idleGrayEngine not running
generatingOrangeAPI task submitted, polling for result
downloadingBlueFetching generated audio from server
decodingPurpleDecoding audio via Web Audio API
readyGoldSegment decoded, waiting to be scheduled
playingGreenAudio is playing through speakers

Generation Flow

  1. Release task — POST to /release_task with prompt, lyrics, duration, and optionally context audio (for repaint mode)
  2. Poll — POST to /query_result every 2 seconds until status === 1 (success) or status === 2 (failure)
  3. Download — Fetch the WAV audio file from the server
  4. Decode — AudioContext.decodeAudioData() converts WAV bytes to an AudioBuffer
  5. Trim — Remove context prefix (repaint only) and end guard tail
  6. Stash — Place in this.nextReady for the scheduler to pick up

3. Repaint-Based Continuity

This is the core innovation. Instead of crossfading between independently-generated segments (which produces audible artifacts), the DJ uses ACE-Step's repaint task type for model-level audio continuity.

How It Works

Previous segment (playable buffer): ├──── context (10s) ────┤──── new audio (30s) ────┤── guard (10s) ──┤ ▲ ▲ repaint_start repaint_end 1. Extract last 10s of previous playable audio as WAV 2. Upload as ctx_audio to /release_task with task_type=repaint 3. Diffusion model uses context as ground truth (masked region) 4. Model generates new audio that naturally continues from context 5. Trim: remove context prefix + end guard tail 6. Result: seamless playback buffer that flows from previous segment

Key Parameters

ParameterUI ControlEffect
context_durationContext Prefill sliderSeconds of previous audio used as context. More = better continuity, slower generation.
end_guardEnd Guard sliderExtra seconds generated at the tail then discarded. Prevents the model from writing a "song ending" at the cutoff point.
weirdnessWeirdness sliderMaps inversely to audio_cover_strength. 0% = faithful continuation, 100% = creative drift.
Why end guard? Music generation models are trained on complete songs. When asked to generate 30 seconds, the model may write a natural ending (fade out, final chord). The end guard adds extra duration beyond what we actually use, so any "ending behavior" falls in the discarded tail instead of the playback region.

4. Audio Scheduling & Gapless Playback

The Web Audio API's BufferSourceNode.start(when) method enables sample-accurate scheduling. The DJ uses this for perfectly gapless playback.

Scheduler (_lookahead())

A 200ms interval timer checks if the currently playing segment is within 2 seconds of ending. If a next segment is ready (this.nextReady), it schedules it to start at exactly the current segment's endTime:

// Gapless: next starts exactly when current ends
this._scheduleSegment(nextSeg, lastSeg.endTime);

Audio Graph

BufferSource (segment N)──▶ GainNode ──┐ BufferSource (segment N+1)──▶ GainNode ──┼──▶ MasterGain ──▶ Analyser ──▶ Destination BufferSource (segment N+2)──▶ GainNode ──┘ │ ▼ Frequency Visualizer

Each segment gets its own BufferSourceNode and GainNode. The gain is constant at 1.0 — no crossfade needed because repaint provides model-level continuity. All segment gain nodes feed into a shared MasterGain (volume control) → AnalyserNode (for the frequency visualizer) → AudioContext.destination (speakers).

Buffer Underrun Recovery

If playback reaches the end of all scheduled segments before the next one is ready, the engine enters a "paused" state. When the next segment finally arrives, it's scheduled immediately at currentTime + 0.1s and generation continues. This causes a brief silence gap but avoids a crash.

Peak Computation

When each segment's AudioBuffer is decoded, peaks are pre-computed and cached in this.waveformPeaks (a Map<segIndex, Float32Array>). The computation takes max(abs(samples)) across all channels for each time bucket of sampleRate / 100 samples.

Coordinate System: Accumulated Duration

The waveform uses an "accumulated duration" coordinate system rather than AudioContext timestamps. This is critical for correctness after seeking:

// _getAccumulatedPlayPos():
// 1. Find which segment is currently playing (via AudioContext time)
// 2. Sum durations of all segments before it
// 3. Add elapsed time within the current segment
// Result: position in "total stream time" space
Why not use AudioContext timestamps directly? After seeking, segments get rescheduled with new startTime/endTime values. The first segment's startTime becomes stale and can't be used as a reference point. Accumulated duration is always correct because it's computed from the segment array's actual order and durations.

6. Click-to-Seek & LIVE Badge

Click-to-Seek

Clicking anywhere on the waveform canvas maps the click position to a segment + offset:

  1. Click X position → time offset from left edge using pixelsPerSec = canvasWidth / 40
  2. Add to timeAtLeftEdge to get absolute time in accumulated-duration space
  3. Walk through segments summing durations to find which segment contains the click time
  4. Call skipToSegment(segIndex, offset)

skipToSegment(targetIndex, offset)

This method handles all seeking:

  1. Stop all currently playing BufferSourceNodes
  2. From the target segment onward, create new source nodes
  3. For the target segment, use source.start(when, offset) to start partway through
  4. Set startTime = t - offset (virtual start) so elapsed calculations remain correct
  5. Subsequent segments start at the previous segment's endTime

Clicking the LIVE badge when behind snaps playback to the last segment via _snapToLiveEdge().

8. Performance Optimizations PERF

Several optimizations prevent the UI from freezing during extended playback sessions:

Unified Animation Loop

Both the waveform and frequency visualizer are drawn from a single requestAnimationFrame loop (_animationLoop()). Previously they had independent rAF loops, which doubled frame overhead and could cause stuttering.

Per-Frame Position Caching

_getAccumulatedPlayPos() performs an O(n) scan over all segments. It's now called once per frame and cached in this._cachedPlayPos, shared by _drawWaveform(), _onWaveformHover(), and _tickNowPlaying().

Pre-allocated Frequency Buffer

The visualizer's Uint8Array for frequency data is allocated once and reused every frame, eliminating per-frame garbage collection pressure.

No Canvas shadowBlur

Canvas shadow operations are expensive compositing passes. The playhead glow now uses a wider semi-transparent stroke underneath a thinner white stroke. Visualizer bar highlights use a brighter fillStyle instead of shadow.

Two-Pass Waveform Drawing

Peak bars are drawn in two passes (played green, then buffered dim green) with visible-range clipping. This minimizes fillStyle state changes from ~4000/frame to just 2 per segment.

9. Memory Management

Continuous playback can generate dozens of segments over time. Memory management prevents unbounded growth:

_cleanupOldSegments()

  • Keeps the last 20 segments with their AudioBuffer references intact (for skip-back)
  • Older segments have their audioBuffer, playableBuffer, source, and gainNode set to null
  • Waveform peaks (Float32Array) are always retained for visual display
  • Cleanup triggers on each segment's source.onended callback

Audio Format

The DJ requests WAV format (audio_format: 'wav') for generation to avoid lossy compression artifacts at segment boundaries. WAV files are larger but decode faster and preserve full quality.

11. Known Issues & Limitations ISSUES

Confirmed Issues

  1. Occasional page freeze during extended playback
    The page has frozen during long sessions (30+ minutes). The tab becomes unresponsive but recovers on navigation/reload. Likely caused by memory pressure from accumulated AudioBuffers or long segment arrays. The unified animation loop and per-frame caching help but may not fully solve it.
  2. Model mismatch: turbo vs SFT
    The UI defaults to 50 inference steps (optimized for the SFT model), but the server may have the turbo model loaded (which is clamped to 8 steps server-side). The user gets turbo quality regardless of the slider setting. Check /health for loaded_model.
  3. LoRA only accepts local paths
    The API's LoRA loader validates with os.path.exists(), so HuggingFace repo IDs can't be passed directly. Adapters must be downloaded first. The PeftModel.from_pretrained() call underneath does support HF repos, but the path check blocks it.
  4. Buffer underrun causes audible gap
    When generation is slower than playback (e.g., 50 inference steps on slow GPU), there's a silence gap between segments. No recovery mechanism blends the transition.
  5. No CORS headers on audio files
    If the API server and HTML are on different origins, audio downloads may be blocked. Both must be served from the same origin or the API must set appropriate CORS headers.

Limitations

  1. Single prompt only — all segments use the same prompt and lyrics. No per-segment variation or playlist/queue system.
  2. No persistence — refreshing the page loses all segments and playback state. No session save/restore.
  3. No waveform export — generated audio can't be downloaded or exported from the UI.
  4. Polling-only API mode — the DJ uses the native polling API (/release_task + /query_result). The completion mode (/v1/chat/completions) is not supported.
  5. No mobile support — the layout assumes a wide desktop viewport. Sidebar doesn't collapse.
